# UI 原语拥有 class 名，页面不写框架 class

状态：accepted

`src/ui/` 下的原语组件（`Button` `Card` `Input` `Select` `Table` `Badge` `Alert` `Modal` `Dropdown`）是控制台唯一允许出现 CSS 框架 class 名的地方。页面与领域组件只通过 props 表达意图：`<Button variant="primary" size="sm">`，不写 `className="btn btn-primary btn-sm"`。

原语的视觉实现只读 `--rlm-*` token，不读框架的语义 class。

## 背景

对齐之前不存在原语层。设计系统实际上是散在 8708 行页面代码里的 Bootstrap class 字符串：`card` 出现 95 处、`btn` 79 处、`alert` 53 处、`modal` 40 处、`badge` 28 处、`form-control` 28 处，另有 50 处内联 `style={{}}`。`src/index.css` 有 125 个 `--rlm-*` token（一次认真的单一真相源尝试），但没有任何组件消费它们——组件消费的是 Bootstrap class。token 层与使用层是断开的。

结果是没有任何一处能回答"主按钮长什么样"：视觉真相等于框架默认值，减去 1868 行样式表里的覆盖，减去页面里的原子 class 组合，减去内联样式。

## 理由

**没有命名的东西无法被复用，也无法被替换。** 现状下"改所有主按钮的圆角"是一次 79 处的搜索替换，且没有任何机制阻止第 80 处写成别的样子。有了 `Button`，它是一次改动。

**token 只有被组件消费才是 token。** 定义了却没人读的 CSS 变量是文档，不是单一真相源。原语层是把 token 和渲染结果连起来的那一层。

**这是卸载 Bootstrap 的唯一可行路径。** 页面直接写框架 class 时，换掉框架等于改所有页面。原语层建立后，框架收缩到九个文件内部，先降级为过渡垫片，再整体删除，页面一行不动。这是"Never break userspace"在内部边界上的同一条原则：给下游一个稳定接口，上游才能自由重写。

**渲染隔离。** 原语不取数、不碰全局 DOM、不依赖路由，因此可以脱离应用外壳渲染。这是组件目录与视觉回归的前提。

## 代价

九个组件要覆盖现有 174 处按钮与卡片调用点的全部实际用法，包括那些现在靠临时拼 class 实现的一次性变体。迁移时必须诚实分类：真变体进 props，一次性 hack 进调用点的局部样式，不允许为了少改代码而给原语开一个万能 `className` 逃生口——那等于把现状原样搬进新目录。

`Modal` 改为受控组件会改变 19 处按 DOM id 操作 modal 的调用点的写法。这些调用点当前依赖 `document.getElementById(id)` 加模拟点击 `data-bs-dismiss` 按钮，同一个 modal 在一个页面里渲染两次就会撞 id——组件变体网格恰恰要并排渲染多个实例。改造是必须的，不是顺手。

## 考虑过的方案

- **保持 Bootstrap class，只抽公共 class 组合成常量**：省下打字，但 class 名仍然散在页面里，框架依旧无法替换，token 依旧没人消费。治标。
- **引入 Tailwind**：把一种原子 class 汤换成另一种，同样没有命名的组件层，且要在重构中途再引入一套构建管线与一套 token 映射。
- **CSS-in-JS**：能解决命名与 token 消费，但引入运行时开销与一套新的心智模型，而项目已经有一份可用的 CSS token 体系，缺的只是消费它的组件。
- **直接上现成组件库（MUI / Ant Design 等）**：控制台的视觉体系（`--rlm-*` 那套鼠尾草绿与雾白）是已有产品决策，套用第三方设计语言等于推翻它；且换成另一个无法替换的外部依赖，问题结构不变。
